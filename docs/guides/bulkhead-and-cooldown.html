Beta

Both protections keep their state in one PHP process. The bulkhead counts the operations in flight in that process only, and a cooldown pauses new operations in that process only. See Limits and non-guarantees.

Code blocks come from examples/09-choosing-policies.php, which tools/run-examples.sh runs and compares with the recorded output.

Bulkhead#

One slow dependency can use up all the concurrent work a process can do, and then everything else waits behind it. A bulkhead limits operations in flight at once, so the rest of the process keeps working.

Shared setup for the snippets on this page
/** Every pipeline below starts from the same two required options. */
$base = static fn(): PipelineBuilder => PipelineBuilder::profile('choosing', 'v1')
    ->partition('shop', 'prod', 'catalog-api')
    ->attemptTimeout(Duration::seconds(2), AttemptTimeoutRequirement::Cooperative);

$ok = static fn(): string => 'ok';
$context = static fn(CompiledPipeline $pipeline): ExecutionContext => $pipeline->newContext(Duration::seconds(30));

The snippet allows one operation in flight. While the outer operation holds the only slot, an inner call is refused:

echo "-- 2. Bulkhead: at most one operation in flight\n";
$pipeline = $base()->bulkhead(1, Duration::seconds(10))->compileInMemory(ExceptionClassifier::create());
$outer = $pipeline->execute(static function () use ($pipeline, $context): string {
    try {
        // Called while the outer operation still holds the only slot.
        return $pipeline->execute(static fn(): string => 'inner', $context($pipeline));
    } catch (AdmissionRejectedException $e) {
        return "inner call refused with {$e->reason()->value}";
    }
}, $context($pipeline));
echo "{$outer}\n";
-- 2. Bulkhead: at most one operation in flight
inner call refused with concurrency_capacity_exhausted

bulkhead(capacity, lease):

  • capacity is the number of slots.
  • A slot is held while an attempt runs and released when it settles. Nothing is held during a retry delay.
  • lease bounds how long a slot stays reserved if its owner vanishes. It must exceed the attempt timeout by more than 1 second.

The refusal is an AdmissionRejectedException with reason concurrency_capacity_exhausted. Your callable did not run.

What a lease does not do

A lease expiring does not stop a callback that is still running. The slot becomes free again, so a new operation may start while the first callback is still running, and the number of callbacks actually running can briefly exceed the capacity. A late release cannot free a newer holder's slot, and every permit ends exactly once. Reqtide cannot stop your code. Make the callable respect the attempt timeout. Before each attempt is sent, Reqtide also checks that the slot's lease still outlasts the attempt. If a slow step before the dispatch used the time, the attempt is not sent and ends with an AdmissionRejectedException with the reason ownership_lease_insufficient. The check uses the local monotonic clock and is not a fencing token.

Cooldown#

When a server answers "slow down, retry after 60 seconds", every other operation in the same partition should wait too, not find out one by one. A cooldown is that shared pause.

cooldown(cleanupGrace) turns it on. cleanupGrace is how long the state is kept after the pause ended. The cooldown activates only when your classifier reports waits, with ExceptionClassifier::retryAfterFrom(). Without one it never activates. Reqtide has no HTTP awareness, so turning a 429 and its header into a Duration is your job.

The snippet below continues the pipeline from Retry and budget, where the first operation was deferred because a 60-second wait does not fit the retry policy's 100 ms maximum delay. The second operation never calls the callable:

try {
    $pipeline->execute($throttled, $pipeline->newContext(Duration::seconds(30), $safety()));
} catch (AdmissionDeferredException $e) {
    echo "next operation deferred with {$e->reason()->value}; the callable ran {$calls} time(s) in total\n";
}
next operation deferred with cooldown_exceeds_deadline; the callable ran 1 time(s) in total

A positive Retry-After extends the shared cooldown for the partition. While it is active, new operations are deferred with cooldown_active, or with cooldown_exceeds_deadline when the wait does not fit the operation's own deadline, as above. The callable ran once in total.

The order of checks#

The cooldown is checked after the circuit and the bulkhead and before the rate limit. If a later check refuses, the permits taken earlier are released. See Concepts.

Testing both#

A bulkhead and a cooldown depend on time. Test them with a virtual clock instead of waiting: see Testing with the virtual clock.
