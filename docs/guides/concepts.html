Four things Reqtide keeps apart#

ThingWhat it isLifetime
PipelineThe configuration (policies and their numbers) plus the state those policies keep: rate-limit tokens, circuit history, retry budget.Built once, reused for every call.
OperationOne logical piece of work you want done, such as "load this order". It has one context, one total deadline and one result.One call to execute().
AttemptOne physical call of your callable. An operation makes one attempt, or several when retries are allowed.One dispatch.
PartitionWhose state this is: application, environment, subject (and optionally a tenant).As long as the pipeline lives.

Keeping them apart is what lets one pipeline serve many concurrent operations without them sharing any per-call data, and what lets a deadline cover all the attempts of one operation.

The pipeline is built once#

PipelineBuilder collects your options and validates the combination. compileInMemory() wires process-local state and returns a CompiledPipeline. The builder has no defaults: a policy exists only if you call its method, and every number is yours.

$catalog = PipelineBuilder::profile('concepts', 'v1')
    ->partition('shop', 'prod', 'catalog-api')
    ->attemptTimeout(Duration::seconds(2), AttemptTimeoutRequirement::Cooperative)
    ->rateLimit(PipelineBuilder::tokenBucket(5, 5, Duration::seconds(1)))
    ->circuitBreaker(PipelineBuilder::lastCalls(10), 4, Ratio::of(1, 2), Duration::seconds(30), 1, 1, Duration::seconds(10))
    ->compileInMemory(ExceptionClassifier::create());

$explanation = $catalog->explain();
echo "profile: {$explanation->profileId->value} {$explanation->profileVersion->value}\n";
echo 'enabled policies: ', implode(', ', $explanation->enabledPolicies), "\n";
foreach ($explanation->capabilityNotes as $note) {
    echo "  {$note}\n";
}

explain() describes what you built without calling anything, touching state or doing I/O. Use it for a start-up log line or to assert in a test that a pipeline is what you think it is:

profile: concepts v1
enabled policies: attempt, retry(maxAttempts=1), rate_limit, circuit
  invocation=synchronous
  settlement=inline_return_or_throw
  attempt_timeout=unsupported
  cancellation=checkpoint_only
  scheduling=bounded_blocking
  queue_ownership=none
  detached_completion=unsupported
  nonblocking=not_claimed
  physical_stop=not_guaranteed
  require_finite_backend_io=false

Read the list of enabled policies first: retry(maxAttempts=1) is always present and means "no retries" until you call retry(). The capability notes are the honest part. attempt_timeout=unsupported and physical_stop=not_guaranteed say that the synchronous runtime cannot stop your callable, and scheduling=bounded_blocking says that retry delays really sleep.

Build the pipeline at start-up and reuse it. It holds the state that makes limits work, so a pipeline you rebuild for every request forgets everything each time. It has no per-operation state, so it is safe to share between operations in one process.

What happens to one attempt#

For each attempt the pipeline asks its questions in a fixed order:

OrderCheckIf it says no
1The deadline and the contextThe operation ends with deadline_exceeded or operation_cancelled.
2Retry eligibility (for attempts after the first)Your last result is returned.
3The minimum remaining allowance for the attempt (attempts after the first)Your last result is returned.
4The retry budget, which reserves one token (attempts after the first)retry_budget_exhausted is recorded and your last result is returned.
5The circuit breakercircuit_open, and your callable does not run.
6The bulkheadconcurrency_capacity_exhausted.
7The shared cooldowncooldown_active or cooldown_exceeds_deadline.
8The rate limitrate.exhausted or a related code.
9DispatchYour callable runs.

If a later check refuses, the permits the earlier checks took are released: a circuit probe is abandoned without counting, the bulkhead slot is freed and a reserved retry token is released. Nothing is held while the pipeline waits between retries. A refusal never reaches your callable and is not counted as a failure of your dependency.

An operation has one deadline and many attempts#

You build one context per operation with newContext(). It carries the total deadline, your statement about repeating the call, an optional fallback and an operation id. The pipeline gives your callable an AttemptContext on every attempt.

$retrying = PipelineBuilder::profile('concepts', 'v1')
    ->partition('shop', 'prod', 'catalog-api')
    ->attemptTimeout(Duration::seconds(2), AttemptTimeoutRequirement::Cooperative)
    ->retry(3, BackoffMode::Constant, Duration::milliseconds(5), Duration::milliseconds(5), JitterMode::None)
    ->retryBudget(10, 10, Duration::seconds(60), Duration::seconds(10))
    ->compileInMemory(ExceptionClassifier::create()->retryOn(Hiccup::class));

$operationIds = [];
$attemptIds = [];
$flaky = static function (AttemptContext $attempt) use (&$operationIds, &$attemptIds): string {
    $operationIds[] = $attempt->operationId->value;
    $attemptIds[] = $attempt->attemptId->lowerHex;
    if ($attempt->dispatchedAttemptNumber < 3) {
        throw new Hiccup('try again');
    }

    return "succeeded on attempt {$attempt->dispatchedAttemptNumber}";
};
$safety = OperationSafety::replayableRead(ReplaySafetyContract::forReadOnlyCallable('list-products', Duration::seconds(3600)));
echo $retrying->execute($flaky, $retrying->newContext(Duration::seconds(30), $safety, operationId: 'concepts-1')), "\n";
echo 'attempts: ', count($attemptIds), ', distinct attempt ids: ', count(array_unique($attemptIds)), "\n";
echo 'distinct operation ids: ', count(array_unique($operationIds)), ' (', $operationIds[0], ")\n";
succeeded on attempt 3
attempts: 3, distinct attempt ids: 3
distinct operation ids: 1 (concepts-1)

What this shows:

  • The operation id is the same on all three attempts, and each attempt has its own attempt id. Logs that name the operation id group the attempts of one operation.
  • dispatchedAttemptNumber counts physical dispatches. This is the number to put in a log line.
  • You build the context right before the call, not at start-up. The deadline starts when newContext() builds it, so an old context would carry an almost spent budget.
  • Never share one context between two operations: it names the operation.

The deadline#

The timeout you give newContext() is the budget of the whole operation: all attempts, all waits between them and a fallback. It must be positive, because an already expired deadline can only fail.

Every snippet in the protection guides starts from the same two required options. This is the setup the deadline example uses:

/** Every pipeline below starts from the same two required options. */
$base = static fn(): PipelineBuilder => PipelineBuilder::profile('choosing', 'v1')
    ->partition('shop', 'prod', 'catalog-api')
    ->attemptTimeout(Duration::seconds(2), AttemptTimeoutRequirement::Cooperative);

$ok = static fn(): string => 'ok';
$context = static fn(CompiledPipeline $pipeline): ExecutionContext => $pipeline->newContext(Duration::seconds(30));
echo "-- 6. Deadline: one budget for the whole operation\n";
$pipeline = $base()->compileInMemory(ExceptionClassifier::create());
$slow = static function (): string {
    usleep(30_000);

    return 'finished late';
};
try {
    $pipeline->execute($slow, $pipeline->newContext(Duration::milliseconds(5)));
} catch (DeadlineExceededException $e) {
    echo "late result replaced by {$e->reason()->value}\n";
}
-- 6. Deadline: one budget for the whole operation
late result replaced by deadline_exceeded

The slow callable above ran to completion. The deadline is checked between steps, not inside your code, so a result that arrives late is replaced by deadline_exceeded; the value itself stays available in the attempt records of detailed mode. Reqtide checks the deadline before each admission and dispatch, so an attempt does not start once the deadline has passed, and a retry whose delay does not fit in the remaining time is not started.

Not a timeout for your code

The deadline does not interrupt a running callable. The attempt timeout you declare with attemptTimeout() as Cooperative is a statement that your code respects the time, for example through a transport timeout. Reqtide cannot enforce it with the synchronous runtime.

The partition#

A partition names whose state a pipeline keeps: an application, an environment, a subject (what you protect, for example catalog-api, never a credential) and optionally a tenant. All the policies of a pipeline share its partition.

One pipeline serves exactly one partition. A context built by a pipeline for another partition is refused before anything is dispatched:

$orders = PipelineBuilder::profile('concepts', 'v1')
    ->partition('shop', 'prod', 'orders-api')
    ->attemptTimeout(Duration::seconds(2), AttemptTimeoutRequirement::Cooperative)
    ->rateLimit(PipelineBuilder::tokenBucket(5, 5, Duration::seconds(1)))
    ->compileInMemory(ExceptionClassifier::create());
try {
    $catalog->execute(static fn(): string => 'never runs', $orders->newContext(Duration::seconds(30)));
} catch (InvalidConfigurationException $e) {
    echo $e->getMessage(), "\n";
}
The execution context partition must equal every selected policy partition.

Choose the subject to match the thing whose capacity you want to protect: one subject per dependency, one pipeline per tenant when limits are per tenant. In the in-memory setup every compiled pipeline owns its backends, so two pipelines never share a quota, even for the same partition. The profile id and version name the configuration. Change the version when the settings change, because state is keyed by it.

What counts as a failure is your decision#

Policies act on the classification of each attempt, and your classifier decides what an outcome means: retryable, a circuit failure, replaceable by a fallback. ExceptionClassifier starts conservative. See Choosing policies.
