A fallback belongs to one operation#

A fallback is a FallbackOperation you attach to a single operation, through the fallback: argument of newContext(). It receives the original Outcome and returns the replacement value. A pipeline with no fallback on the context never replaces anything.

/** @implements FallbackOperation<string> */
final class CachedCatalog implements FallbackOperation
{
    public function invoke(Outcome $original, ExecutionContext $context): string
    {
        return 'cached catalog';
    }
}

Two things must both be true before a fallback replaces a failure: the operation carries a fallback, and your classifier marked the exception fallback-eligible with ExceptionClassifier::fallbackOn(). The default is none. An exception you did not list is returned to you.

Choose what it may replace#

By default a fallback may only replace what your callable did. With FallbackScope::IncludeAdmissionRefusals it may also replace a circuit, bulkhead, rate or cooldown refusal. This snippet spends the only rate-limit token and then makes a second call under each scope:

Shared setup for the snippets on this page
/** Every pipeline below starts from the same two required options. */
$base = static fn(): PipelineBuilder => PipelineBuilder::profile('choosing', 'v1')
    ->partition('shop', 'prod', 'catalog-api')
    ->attemptTimeout(Duration::seconds(2), AttemptTimeoutRequirement::Cooperative);

$ok = static fn(): string => 'ok';
$context = static fn(CompiledPipeline $pipeline): ExecutionContext => $pipeline->newContext(Duration::seconds(30));
echo "-- 5. Fallback: replace failures, and optionally refusals\n";
$build = static fn(FallbackScope $scope): CompiledPipeline => $base()
    ->rateLimit(PipelineBuilder::tokenBucket(1, 1, Duration::seconds(3600)))
    ->fallbackScope($scope)
    ->compileInMemory(ExceptionClassifier::create()->fallbackOn(\Throwable::class));
foreach ([FallbackScope::BusinessOutcomesOnly, FallbackScope::IncludeAdmissionRefusals] as $scope) {
    $pipeline = $build($scope);
    $pipeline->execute($ok, $pipeline->newContext(Duration::seconds(30))); // uses the only token
    try {
        $value = $pipeline->execute($ok, $pipeline->newContext(Duration::seconds(30), fallback: new CachedCatalog()));
        echo "{$scope->value}: second call returned '{$value}'\n";
    } catch (AdmissionRejectedException | AdmissionDeferredException $e) {
        echo "{$scope->value}: second call refused with {$e->reason()->value}\n";
    }
}
-- 5. Fallback: replace failures, and optionally refusals
business_outcomes_only: second call refused with rate.exhausted
include_admission_refusals: second call returned 'cached catalog'

The default scope lets the refusal through, so you still know you are being throttled. With IncludeAdmissionRefusals the second call returns the cached value, and the refusal is not lost: detailed mode keeps it as policyCause. Choose the second scope deliberately. A fallback that hides refusals also hides that you are being throttled.

fallbackScope(IncludeAdmissionRefusals) needs at least one admission policy (a rate limit, circuit breaker, bulkhead or cooldown); the builder rejects the combination otherwise.

What a fallback never replaces#

  • A deadline. If the total deadline passed, the result is deadline_exceeded.
  • A cancellation. This also holds while the fallback runs: a cancellation requested during the fallback makes the result cancelled, and detailed mode still holds the value or exception the fallback produced. A deadline that passes during the fallback wins over the cancellation.
  • An infrastructure failure, such as an unreachable state backend. Reqtide does not invent behavior when its own state is down.

A fallback shares the operation's total deadline: it runs inside the same budget as the attempts before it.

When the fallback itself fails#

A fallback that throws is reported as FallbackFailedException in simple mode, with the fallback's exception as getPrevious(), and as the disposition fallback_failed in detailed mode. The original failure is retained on the exception. The annotated script 04-fallback.php shows both.
