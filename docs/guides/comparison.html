Comparison with other libraries

This page reports a behavior comparison that the Reqtide author wrote and ran. It is not an independent review, and it does not say which library is better. Use it to see which behaviors differ and decide whether they matter to you.

Applies to the development tree before the 0.1.0 release. Run on 2026-10-09 with PHP 8.4. Read the caveats before the table.

What was compared#

The harness lives in benchmarks/comparison/ in the repository. It has 21 scenarios written without any library's name in them, such as "the total deadline spans retries and waits" or "a late release cannot free someone else's permit". Each scenario was run against a pinned release of six other libraries through a small adapter, and against Reqtide's public API. All time is virtual, so nothing sleeps and results repeat.

A scenario is graded only for libraries whose scope can express it. A rate limiter is not graded on retries. That is why most cells are "not applicable".

Two more scenarios are informational and not counted. Rows do not add up to the same total, and counts are not comparable across rows. A library with a narrow scope has few graded scenarios by design.

Caveats#

  • The same author wrote everything. The scenarios, the adapters for the other libraries and the Reqtide adapter come from one person, and the scenarios came from the project's own gap research. Scenarios may favor what Reqtide is built to do.
  • Some Reqtide results rest on choices the adapter made. Reqtide has no defaults, so the adapter picked its values. Six scenarios (retry budget size, POST not retried by default, abandoned probe, late release, typed rejections, clock regression) depend on such choices or on a lenient reading, and the harness flags each one. The other libraries ran on their own defaults.
  • S15 is the one Reqtide failure, and it is by design. A request cancelled after admission and before dispatch keeps its rate unit, because Reqtide never refunds a rate charge. The scenario counts that as a failure. The other libraries could not run the same sub-case, so this row is not like for like. Two of them under-count quota when the limiter sits outside the retry layer, and are graded as composition-dependent.
  • S12 is contestable. The scenario says peak concurrency must never exceed one. No lease-based bulkhead can satisfy that literally: once a lease expires, the first callback may still be running when the next one is admitted. The cell is graded on whether a third caller is let in while the second is running.
  • A passing cell is narrow. It means the expected behavior was seen in that one scenario with that configuration.
  • Only process-local memory and a virtual clock were exercised. The page says nothing about speed, shared state, real transports or production readiness. For ganesha only its APCu adapter ran, against an in-process stand-in for the APCu functions.
  • Versions move. Other libraries ship fixes. Results describe the versions in the table on the day of the run.

How to read it#

  • If you need only one protection, use the library built for it. A dedicated rate limiter or circuit breaker may fit better than a pipeline.
  • Reqtide's pitch is the combination: one fixed order of decisions, one deadline across all of them, typed results, and tests under virtual time.
  • If a difference in the table matters to you, run the scenario against your own configuration.

Reproduce#

The harness needs PHP 8.4 or newer, because two of the compared libraries require it. From a clone, with Docker, install the pinned dependencies once and then run it:

docker compose -f tools/docker/compose.yaml run --rm -e COMPOSER_VENDOR_DIR=/app/build/comparison/vendor php84 composer install -d benchmarks/comparison
docker compose -f tools/docker/compose.yaml run --rm php84 php benchmarks/comparison/run.php

The harness README has the details.
