Limits and non-guarantees

After this page you know what Reqtide PHP does not do today, what it never promises, and what it commits to. Read it before you put the library in front of real traffic.

Applies to version 0.1.0 (beta). Checked 2026-10-15.

Beta status#

  • The first release is 0.1.0 (see Install).
  • Version 0.x is beta: a public name or behavior can change between minor versions, and every change is listed in the changelog.
  • The core package enaxon/reqtide keeps its state in one process. Two separate packages exist and are described at the end of this page, and in Shared state with Redis and Guzzle requests with Reqtide. A plan is not a promise.
  • Tests and examples were run in Docker on the command line with PHP 8.3, 8.4 and 8.5. PHP-FPM is covered by one CI lane: PHP 8.4, nginx, six workers and Redis 8.2.10 (process-local state starts fresh per request, Redis state is shared and correct under concurrent requests, a bulkhead, a deadline and a retry). Other PHP versions under FPM, the Guzzle client under FPM, Apache and other web server setups were not run. A passing run in Docker or in CI is not a support or production claim.
  • No speed, capacity or latency claims are made. The only figures are the rough cost numbers in Guzzle requests with Reqtide, measured once on one laptop with large noise.

What version 0.x does not do#

LimitWhat it means for you
State lives in one PHP process.Under PHP-FPM a pipeline built inside a request starts every request with a full quota and a closed circuit. Limits do not add up across requests, workers or servers. Use it where one process lives long enough to matter (a worker, a CLI job, a daemon), or use the separate Redis package (see Shared state with Redis).
No shared quota in the core package.A rate limit in the core package protects one process. Ten workers each get the full limit. A shared quota needs the separate Redis package.
A running callback is not interrupted.The total deadline is checked between steps. If your callable runs past the deadline, it runs to the end and the late result is reported as DeadlineExceeded. The synchronous runtime cannot enforce an attempt timeout, so you declare it as Cooperative and your code must stop itself.
A bulkhead lease is not a physical stop.When a lease expires, the callback may still be running. The permit is free again, but the work is not stopped. Another caller can then be admitted past the bulkhead limit, and a slow call that fails late does not count toward the circuit breaker. Give your callable its own hard timeout, shorter than the attempt timeout (for example the timeout of your HTTP or database client). The Guzzle package does this for you. When a lease ran out, the result carries the diagnostic concurrency_release_stale. Before each dispatch Reqtide checks, with its own monotonic clock, that a concurrency permit and a half-open probe still outlast the attempt; if not, the attempt is not sent and ends with ownership_lease_insufficient. This check is local and conservative. It is not a fencing token, and a pause after the check cannot be seen. A system that must be protected from a paused or slow holder needs its own fencing, for example a version or token that it checks itself; Reqtide does not provide a fencing token.
Rate charges are not refunded.A call cancelled after admission and before dispatch still used its unit. Quota used is not the same as requests sent.
No exactly-once execution.A call may run more than once, or once with an unknown result. Reqtide reports what it knows; it cannot make your operation idempotent.
No retry of anything you did not allow.A retry needs your assertion that repeating the call is safe, a retry budget and a retryable exception class. Reqtide never infers safety, and it has no HTTP knowledge.
No defaults.You choose every timeout, limit, window and delay. The numbers in the examples make behavior visible and are not recommendations.
No failover guarantees.The Redis package keeps its state in Redis memory. A restart without persistence, a flush or a failover loses it. Strict failover guarantees are out of scope, and Sentinel, Cluster and Valkey are not supported.
Not an HTTP client, a queue or edge protection.Reqtide wraps a callable. It does not send requests, store work for later or defend a public endpoint.
Not in the first release.Hedged requests, cache revalidation, a failed-work queue and waiting queues.

What Reqtide commits to#

These hold for the local part and are covered by its tests.

  • One operation, one deadline. A retry whose delay cannot fit in the remaining time is not started.
  • Your exceptions come out unwrapped. Reqtide's own refusals are typed exceptions that carry a machine-readable reason. See Error handling.
  • Nothing is retried unless you say so. Retrying needs your safety assertion, a retry budget and a retryable exception class.
  • A permit is released at most once, or ends by lease expiry. A circuit permit or a concurrency permit is released on success, on exception and on cancellation. If a release fails, Reqtide records the failure and the permit ends when its lease expires.
  • Failing state is not hidden. If a state backend fails, the protected call does not run, and Reqtide does not invent fallback behavior. A failing observer or bookkeeping step after the call never replaces your result.
  • Time is monotonic and integer-based. A clock that steps backwards never refills a quota.
  • State is bounded. At its ceiling a memory backend frees expired records, then evicts the oldest bookkeeping that protects nothing, then rejects new partitions. It never evicts an active permit, a budget balance or an open circuit.

Versioning and compatibility#

  • Semantic versioning. Before 1.0 a minor version can change the API. Every break is listed in CHANGELOG.md. From 1.0 only a major version breaks it.
  • One version for the three packages. enaxon/reqtide, enaxon/reqtide-redis and enaxon/reqtide-guzzle are released together, and each adapter requires exactly the same version of the core.
  • What the promise covers. Public classes, interfaces, enums, constants and methods that are not marked @internal; the string values of ReasonCode and the members of the Problem JSON, including its type identifier. A new reason code is not a break, so handle unknown codes.
  • What it does not cover. Anything marked @internal, the test helper internals, the Redis key layout and Lua scripts (the registry schema version is checked and a mismatch is refused), and the text of messages.
  • Do not extend. Classes are final. The two abstract exception bases are for catching, not for extending.
