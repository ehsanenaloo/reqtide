Alpha

Process-local, in-memory state only: every limit applies inside one PHP process. Under PHP-FPM a pipeline built inside a request starts every request fresh. See Limits and non-guarantees.

Reqtide ships no defaults for timeouts, limits, windows or delays, and these guides recommend no numbers: the right values depend on your dependency, your traffic and your risk.

Every code block in the protection guides comes from examples/09-choosing-policies.php or a sibling example, which tools/run-examples.sh runs and compares with the recorded output. The numbers in them make each protection visible in a few lines. They are not advice.

The classifier decides what counts#

Policies act on the outcome of each attempt, and your classifier decides what an outcome means. ExceptionClassifier starts conservative:

  • a returned value is a success;
  • an exception is not retried and not replaced by a fallback unless you list its class (retryOn(), fallbackOn());
  • every exception counts as a circuit failure, unless you list its class in ignoreForCircuit() (for example the caller's own validation error) or narrow the failures with countAsCircuitFailure().

unacceptableValuesWhen() marks a returned value as a failure (a circuit failure, never retried, never replaced). retryAfterFrom() extracts a wait from an exception. The decision table is in the ExceptionClassifier docblock. Rate-limit, circuit, bulkhead and cooldown refusals, cancellations and storage errors are neutral: they never count as dependency failures.

An exception nobody listed is not retried, because repeating an unexpected failure is a decision you must make explicitly. It is still counted as a circuit failure, because a circuit that ignored unknown failures would stay closed against a dependency that fails in a way nobody anticipated. Matching uses instanceof, so a listed parent class or interface covers its subclasses.

Every snippet starts the same way#

The protection guides build their pipelines from two required options. The attempt timeout is required. Cooperative means your code respects the time; the synchronous runtime cannot stop it. The deadline you pass to newContext() is a separate, total budget for the whole operation.

/** Every pipeline below starts from the same two required options. */
$base = static fn(): PipelineBuilder => PipelineBuilder::profile('choosing', 'v1')
    ->partition('shop', 'prod', 'catalog-api')
    ->attemptTimeout(Duration::seconds(2), AttemptTimeoutRequirement::Cooperative);

$ok = static fn(): string => 'ok';
$context = static fn(CompiledPipeline $pipeline): ExecutionContext => $pipeline->newContext(Duration::seconds(30));

What is checked, in which order#

For each attempt: the deadline and context first, then retry eligibility, the minimum remaining allowance and the retry-budget reservation (the last two only for attempts after the first), then the circuit, the bulkhead, the shared cooldown and the rate limit, then the dispatch. If a later check refuses, the earlier permits are released. Nothing is held during a retry delay. Concepts shows the order as a table.

Sizing checklist#

Reqtide validates the combination when you compile, and the messages name the option. These are the constraints it enforces, not recommended values:

  • every lease (bulkhead, circuit permit lease, retry-budget reservation lease) must exceed the attempt timeout by more than 1 second;
  • retry() with more than one attempt needs retryBudget(), and a retryBudget() without it is rejected;
  • circuit minimum samples cannot exceed a count window; the probe success threshold cannot exceed the probe capacity;
  • fallbackScope(IncludeAdmissionRefusals) needs at least one admission policy.

Everything else (limits, windows, delays, pool sizes) is a decision about your dependency. Measure it, record it, and test the pipeline under virtual time (Testing with the virtual clock).
